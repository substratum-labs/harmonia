# Harmonia 最小形式核心设计草案

状态：已获 Yong 批准，第一阶段进入托管实施。修订日期：2026 年 10 月 4 日。方向：基础先行，Kadmos 上层应用，验证后扩展。

Harmonia 是独立的分布式算法形式化项目。它建立执行语义、证明基础和通向实现的保证链，Kadmos 是首个应用。本设计确定最小核心的边界和验收义务，尚不是实现计划，也不表示下述能力已经完成。

核心决定是：以固定版本的 Lean 4 为基础，由 Harmonia 掌握语义与接口；参考 Veil，选择性移植机制，不将 Veil 作为核心依赖。先定义系统状态、观测、动作与转移关系、执行历史、可达性及安全性质，再建立节点、消息和故障语义，然后构建面向 Kadmos 的可执行上层。验证结果决定抽象如何修订，以及是否进入其他应用。

通用转移系统不预设 checker、拒绝 verdict、savepoint、directive 或回滚。Kadmos 上层在通用关系框架内解释这些操作。对可执行应用，参考执行、验证条件与目标代码共享同一行为定义并承担对应证明；纯关系规约也可以使用核心，但不自动获得解释器或代码生成能力。

## 项目目标与首期范围

长期支持分布式算法的安全性、明确假设下的活性、故障语义、可复用元定理及实现精化。首期采用“通用基础、Kadmos 上层、验证反馈”的顺序，不从 Kadmos API 倒推出核心概念。

基础阶段先提供带标签与观测的状态转移系统、初态、有限执行、可达性、归纳安全性与基本精化规则，再建立有限配置中的节点、局部执行、消息与明确的故障配置。系统可以是非确定性的；可执行性是后续应用需要满足的条件。

Kadmos 阶段提供带类型请求、顺序赋值、不变量检查、接受与拒绝 verdict、directive、savepoint 以及本地回滚。结算状态机与任务租约是首批验证对象，不成为所有分布式协议必须采用的机制。

完整 Raft、BFT、FLP、CAP、动态成员变更、自动发现任意归纳不变量、全应用验证和运行时性能承诺不属于首期。TLA+ 可用于具体问题的临时建模，不建设并行的正式编译路线。首期验证通过后，再根据实际缺口选择第二个应用或更复杂协议，不提前锁定完整功能路线。

## 结构与依赖边界

以下是逻辑模块边界，最终文件划分由实现计划确定。基础层不能导入 Kadmos 或依赖其数据类型，验证工具不能改变所验证的语义。

| 层与模块 | 负责内容 | 依赖规则 |
| --- | --- | --- |
| 基础 Core | 参数化状态、动作、观测、初态、转移关系、历史、可达性、安全性与基本精化定理 | 不导入 DSL、求解器、checker 或 Kadmos |
| 分布式 Distributed | 节点配置、局部处理、消息、网络、调度、故障与恢复模型 | 实例化 Core；不强制使用门禁或回滚 |
| 应用 Applications/Kadmos | World 语义、带类型动作表示、参考解释器、verdict、directive 与 savepoint | 依赖基础；分布式切片再依赖 Distributed |
| 验证 Verification | 支持子集的 VC 生成、有限模型探索、求解器适配和反例回放 | 读取已定义的语义与可执行表示 |

首期保留仓库已有的 Lean 4.16.0 固定版本，先检查所选机制在该版本上的可实现性。不为了移植 Veil 的新语法直接升级工具链。确需升级时，单独提交兼容性评估和全部证明重检。

## 通用状态转移基础

状态 S、动作 A 和观测 O 是类型参数。一个系统提供初态谓词 Init 和关系 Step(s, a, o, s')。Step 可以允许多个后状态，也可以没有适用步骤，不默认是决定性函数。动作是否原子取决于该实例选择的粒度；基础不承诺多次物理 IO 全部完成或全部撤销。

状态包含该模型需要的信息，不默认要求 context、阶段字段、durable 字段或快照。观测是模型选择对外解释的行为，如收到请求、输出结果或提交；内部步骤可以标记为不可见。模型必须明确哪些信息可以被观察，不能把不同应用的“状态相同”当作默认行为等价。

有限执行历史记录初态和带标签步骤。有效历史要求每一步满足 Step；可达性由初态与有效有限执行定义。安全性质表达为可达状态上的谓词，必要时通过历史状态表达。首先证明历史前缀有效、执行连接、一步可达性闭包与归纳不变量原理：初态满足 I 且每个 Step 保持 I，则每个可达状态满足 I。

核心提供观测映射与前向模拟的陈述和基本保持定理。首期先处理明确的一步对应或有限内部步骤对应；不预设弱双向模拟，不由安全性模拟推出公平性或活性。初态存在性和背景假设一致性需要独立证据，避免空模型使安全性成立。

核心不内置 Accepted、Rejected、Disabled 或 Unknown。应用可以把拒绝表示为带拒绝观测的状态不变步骤，分布式模型可以把故障表示为改变进程状态的步骤。只有在指定观测接口下，才能判断它们是否可忽略或对应停顿。

## 分布式执行与故障

节点类型是参数，初期实例使用显式有限成员集合。全局不变量、调度和收发步骤都限制在配置成员内，集合中的重复成员必须拒绝。局部处理函数只能读取自己的局部状态、收到的消息和显式证据；全局性质在证明层观察系统，不作为节点运行时可直接读取的 guard。

节点状态分为 durable、volatile 和进程运行状态。Crash 清除协议指定的 volatile 信息并保留 durable 信息；Recover 按明确的恢复函数重建局部状态。存储服务自身丢失提交或发生故障转移属于额外故障模型，不能由进程恢复假设顺带保证。

网络以消息出现次数为语义，使用 List 实现时需定义表示关系并避免将列表顺序当成网络 FIFO 保证。消息逻辑身份与某次传输实例的身份分开；复制可以产生相同逻辑请求的新传输实例。发送、投递、丢弃和复制是分开的全局步骤，协议自行决定去重。

超时是调度输入，不表示另一节点已崩溃。故障配置明确选择允许的环境步骤；无限丢包配置不能作为经典 FLP 的网络假设。

有限探索必须声明节点、数据域、消息数量与历史深度边界。字符串等无限域需要明确的有限实例；达到搜索边界时标记验证范围或未完成，不能静默截断行为后宣称任意执行安全。

有限历史先服务安全性与反例回放。无限执行、公平调度与活性保留扩展边界，不在首期默认施加公平性，也不把未找到安全反例解释为系统一定终止。

## Kadmos 上层的类型与动作语言

Kadmos 上层的首期 IR 支持 Bool、有限枚举、声明范围内的整数、字符串相等，以及显式的可选值。缺失值、null、布尔值和整数彼此不同。请求解码必须先验证类型，解码失败产生拒绝，不能借类型转换使错误输入合法。

表达式只包含变量读取、常量、同类型比较、布尔逻辑和受限整数运算。支持加减、分支、有限顺序赋值和纯 helper；首期不支持任意 Lean IO、循环、递归、不受限制的函数值、隐式数值转换或浮点运算。

数学整数与 JavaScript number 的行为必须通过数值适配连接。只检查最终值不足以排除中间结果的精度损失。首期认证子集要求证明每个整数运算的输入和中间结果都在安全范围内；无法建立此条件的表达式不得获得跨语言认证。乘除等扩展应另行规定精度、舍入和失败语义。

动作定义包括源阶段、目标阶段、输入类型、guard、effects 和输出 intent。guard 在前状态求值；effects 按声明顺序读取和更新候选上下文。为对应 Kadmos，effects 中的 `state` 读取目标阶段，其余上下文读取当前候选值。该规则由适配配置显式规定，不能依赖各后端的默认行为。

持久的不变量只读取状态。读取当前请求的条件属于请求验证、guard 或单次动作的后置条件；它们不直接作为恢复后仍成立的状态不变量。

## Kadmos 上层的本地执行与回滚

Kadmos 上层的本地解释器是纯函数。一个动作先在私有候选状态上求值，不直接执行写盘或发包。

| 执行结果 | 对 checker 的影响 | 返回信息 |
| --- | --- | --- |
| Rejected | 保持受保护状态、上下文、接受历史和已有 savepoint | 明确原因，不授权 intent |
| Accepted | 发布通过检查的候选状态，保存接受前快照 | 新状态、声明的 intent、动作身份与版本 |

非法动作、guard 不满足、输入错误、求值失败、上下文越界和不变量失败都得到明确拒绝。拒绝诊断单独保存，不能被混入已接受历史。非确定性环境动作中的 Disabled 表示未启用，不替代 API 的拒绝 verdict。

接受只授权 intent，并不声明物理副作用已发生。Kadmos 动作返回显式 intent，并将其适配为 directive；Core 不规定 intent 的类型。返回的 intent 必须与该动作的声明一致。请求附带 proposed directive 时，Kadmos 适配按现有规则严格检查它与声明的 directive 是否一致，不通过默认转换获得授权。

首期 Kadmos 兼容配置使用单一 outstanding 操作并串行访问 checker。接受后到操作被分类为成功、确认未提交或结果未知之前，不允许另一个接受动作覆盖 savepoint。这是调用契约，不是当前 TypeScript `#busy` 已经提供的异步互斥保证。

合法回滚只恢复该操作的本地快照并消耗 savepoint。拒绝后的回滚不得误撤销另一个已接受动作。没有 savepoint 或操作身份不匹配时返回明确错误；更复杂的多操作事务不在首期。

回滚的物理解释受结果分类约束：确认未提交时可以恢复并按契约重试；结果未知时，即便恢复了本地快照，也必须记录未知状态并进行查询或去重，不允许据此宣称远端被撤销。

## Kadmos 租约切片的副作用与提交

一次物理操作最少经历授权、发送请求、权威存储处理、回复与本地对账。中间步骤均允许进程崩溃和网络延迟。

```text
本地授权并生成 intent
          ↓
发出带操作身份与租约证据的请求
          ↓
权威存储检查状态与租约并提交
          ↓
回复到达 或 回复丢失
          ↓
确认结果 或 读取权威状态并对账
```

结果分类为 Committed、NotCommitted、Unknown。超时或连接异常默认只能给出 Unknown，除非执行适配能证明请求未被提交。

首期租约实例假设一个权威存储，其条件检查和结果更新原子执行，已提交结果在本模型覆盖的进程崩溃下保留。检查目标状态、租约身份以及必要的版本；状态已终结或租约失效时，拒绝新提交。重复请求通过稳定操作身份或终态检查消除重复结果写入。

这保证任务结果提交，不保证用户任务代码只运行一次。支付、邮件等外部服务需要自己的去重契约，不从任务状态存储的原子性推出。

Kadmos Redis 实现检查 state 与 token；Harmonia 的 epoch 模型需要定义两者的对应关系，包括 token 不复用、任务实例身份和恢复规则。Redis 脚本原子执行不自动证明存储持久性、异常后整段撤销或发布事件与结果存储一致。首期可以把这些列为边界假设，不能隐藏在“门禁保证”中。

## 执行语义与验证条件的连接

Core 允许直接声明关系规约。对于 Kadmos 等可执行应用，应用 IR 的参考解释器产生明确结果，应用的 Step 关系由该解释器定义：接受对应候选后状态，拒绝对应带标签的状态不变步骤。分布式环境步骤通过 Distributed 的规则组合，SMT 查询不能另写一份行为。

证明首先依据已经选定的关系规约陈述性质；当有可执行表示时，再证明解释器、关系、VC 与导出的对应。不能要求通用核心中的每个关系都有可判定 guard、可枚举状态或可生成实现。

验证条件首先是 Lean 中的命题。Core 的基本义务是初态和所有 Step 保持不变量。Kadmos 上层再承担以下义务：

```text
初始状态合法
合法输入下，I(s) 且动作接受为 s'，推出 I(s')
动作拒绝，推出完整受保护状态保持不变
在 savepoint 调用契约下，回滚恢复先前快照
```

同时验证接受行为与动作语义一致，避免“总是拒绝”满足安全性却失去正确执行能力。协议在不依赖事后不变量拦截时安全，与门禁拒绝危险候选后安全，是两种独立主张。

每项 VC 生成规则都需要 soundness 定理：生成的条件成立，推出源动作的对应性质。语法宏只负责构造 IR，不承担语义正确性的最后裁决。复杂的替换和状态更新优先建立小引理，避免直接展开整个执行器证明每个协议。

SMT 后端只编码声明支持的片段。首期优先有限域与无量词的受限整数条件，不承诺任意参数化协议都落在 EPR。后续 EPR 配置须检查完整 VC 的量词与函数依赖；数学语义的表达能力不等于 SMT 自动化能力。

求解器返回 SAT、UNSAT、Unknown、Timeout 或 Error。只有经 Lean 检查的证明可以标为 Proved。未经检查的 UNSAT 标为 SolverChecked，并记录查询、编码版本与求解器版本；重建失败不得降级后继续标为 Proved。

归纳反例 CTI 与从初态可达的执行轨迹分开。有限模型检查记录具体域、边界、故障配置及背景假设；反例需在参考解释器中回放。除非实现了候选生成与反例反馈循环，不把这些能力命名为 CEGIS。

## 目标代码与可信边界

目标代码使用明确的输入解码与状态编码。声明关系 R 连接源状态与目标状态，再证明接受、拒绝、上下文更新、intent 和回滚的对应。Lean 编译出的程序与 TS、Python、C 的表示转换是不同的保证边界。

首期证据分层记录，不合并成一个“已验证”标签：

| 证据 | 可以主张什么 |
| --- | --- |
| Lean 内核检查的定理 | 在陈述假设下，所指语义的性质成立 |
| 未重建证明的 SMT UNSAT | 指定编码获得求解器支持 |
| 有限域模型检查 | 在声明域与配置内完成探索 |
| Lean 与 TS/Python 差分 | 指定模型和请求序列的实现一致性证据 |
| 代码生成对应定理 | 指定目标与支持范围内的语义保持 |
| 宿主执行契约及验证 | 在接入、并发、存储与恢复假设下传递性质 |

证明记录包含模型、假设、工具链、源版本、支持配置和目标版本。禁止 `sorryAx` 或未声明的协议公理进入正式认证；使用 native 证明机制时明确增加的可信组件。性能数据单独记录，不能替代正确性证据。

## Veil 机制的取舍

| 机制 | 首期决定 | 原因与条件 |
| --- | --- | --- |
| 状态转移、可达性、归纳不变量的组织 | 基础阶段借鉴思路，独立定义 | 不以 checker 的执行结果限定核心 |
| WP 与动作解释的对应 | Kadmos 上层阶段再评估小范围移植 | 先确定应用语言；不直接引入整套 Loom 单子结构 |
| 符号与具体状态表示的连接 | 保留这一设计原则 | 首期简单表示足够，优化需要表示保持证明 |
| 有限状态探索与带标签反例 | 独立实现最小版本，评估移植局部算法 | 共享参考解释器与回放格式 |
| SMT 编码与证明重建 | 通过可替换后端接入 | 后端内部类型不进入 Core 的公开接口 |
| Veil DSL 与 elaborator 整体 | 不直接移植 | 不引入其默认原子性、Disabled 或其他隐含语义 |
| UI、复杂优化与协议案例全集 | 首期不移植 | 尚不服务最小保证链 |

代码移植前记录来源提交、许可、依赖闭包、语义前提和替换范围。遵守复制代码及其依赖各自的许可要求。上游改进逐项评估，不维持持续合并要求。独立演进不等于保证内容在修改语义后自动继续成立。

## 阶段计划与验收

以下是架构阶段顺序，尚不是文件级实现计划。每个阶段只有达到自己的验收条件，才推进相应上层；Kadmos 的具体结果用于检验基础，不用于预先强制基础采用门禁 API。

| 阶段 | 主要交付 | 验收条件 |
| --- | --- | --- |
| 一 通用转移基础 | 状态、动作、观测、初态、有限历史、可达性、安全性与基本精化 | Lean 通用定理通过；接口不引用 Kadmos、savepoint 或 checker；初态与假设有一致性证据 |
| 二 最小分布式语义 | 有限成员、局部处理、消息身份与重复、投递、丢弃、调度、明确的进程崩溃与恢复配置 | 用没有 checker 的小型消息实例证明或检查成员约束、局部读取和消息消费；证明或展示消息复制下的行为区别 |
| 三 Kadmos 上层 | World 子集、带类型动作 IR、参考执行器、verdict、directive、savepoint 与回滚 | 证明动作与基础 Step 的对应；证明类型和顺序赋值、拒绝保持状态及合法回滚 |
| 四 Kadmos 验证 | VC 对应、可回放反例、TS/Python 差分、租约与提交恢复切片、最小目标导出对应 | 分别记录通用证明、有限检查和实现测试；覆盖未知结果与旧 worker；对选定目标建立对应证明 |
| 五 验证反馈与扩展选择 | 基础修订记录、可复用与应用专属机制清单、下一应用候选比较 | 根据已发现缺口决定是否提炼共享 DSL、扩展故障模型或进入另一协议；不以完成 Kadmos 为通用性证明 |

第一阶段不先建设完整 DSL、SMT 或代码生成器。第二阶段只提供第三、四阶段确实会使用的分布式基本语义，不试图一次建立所有故障模型。第三阶段的类型、拒绝与回滚是应用设计，不反向放入 Core。

第四阶段至少覆盖：合法顺序赋值、非法输入、拒绝后 savepoint 保留、回滚后的快照、旧 worker 提交、重复请求、已提交但回复丢失、进程恢复和存储拒绝。有限探索明确域与边界；无 `sorryAx` 的证明和差分测试分别验收，不能互相替代。

反馈必须区分三类修改。基础缺口包括观测不清、步骤粒度不足或模拟关系无法陈述，应修订基础并重检依赖证明；Kadmos 特有问题留在应用层；仅影响性能或求解成功率的问题优先修改工具层，不改变协议语义来迎合求解器。

第一次对外主张为“建立并验证通用转移基础，以及其 Kadmos 上层在指定子集中的执行性质”。租约切片的全局保证另列存储与故障假设。升级到“生成实现正确”必须具备所指目标的对应定理，升级到任意规模协议安全必须有参数化证明。第二个不同应用成功后，才有更强的通用性证据。

## 后续扩展的选择依据

不预设下一个项目一定是完整 Raft、BFT 或元定理机械化。Kadmos 验证后，比较候选是否检验新的语义能力、能否复用既有证明、是否有明确的实现需求，以及新增工作量是否可控。

如果主要缺口是状态表示和更新，优先提炼共享动作语言；如果主要缺口是存储恢复，优先完善故障与精化模型；如果基础和 Kadmos 上层已稳定，选择一个不同应用检验通用性；如果进入 quorum 或不可能性问题，先补足对应网络、故障及公平性假设，再建立元定理。

该选择依据不降低 Harmonia 的长期使命，而是让扩展顺序由验证证据决定。

## 设计取舍与后续审阅

独立核心增加维护和证明成本，也让分布式语义按 Harmonia 的目标演进。基础先行不意味着先建设完整理论体系，而是先完成最小可用的通用定义和定理，再用 Kadmos 检验它们。

此次修订只更新设计文档。重点审阅：关系基础与可执行上层的区分、Core 不包含 Kadmos API、分布式基本语义的范围，以及验证后决定扩展的验收原则。通过审阅后，仅为第一阶段制定文件级实施计划；协议代码、编译器和生成门禁仍不在此次修改范围。
